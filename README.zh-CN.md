# Brief to Build

> **从一句口头要求到可执行项目计划。**

[![Agent Skill](https://img.shields.io/badge/Agent-Skill-6f42c1)](https://agentskills.io/)
[![License: MIT](https://img.shields.io/badge/License-MIT-green.svg)](LICENSE)

`brief-to-build` 可以把领导录音、会议转写、聊天记录、附件和未经整理的口头要求，转化成一套真正能由团队和 Agent 执行的项目方案。

只需提供原始材料，它就会提取真正的要求，只澄清会改变结果的关键问题，并生成：

- 可追溯的需求基线；
- 按顺序拆解的执行计划；
- 可直接交给其他 Agent 的任务 Prompt；
- 验收标准与需求变更记录。

整个过程可以概括为：

```text
一句口头要求 → 清晰需求 → 可执行步骤 → Agent Prompt → 可验证交付
```

## 从一句口头要求到可执行项目计划

领导可能会说：

> “根据会议录音和我发给你的材料，研究一下 AI 原生数据库。对比主要产品和最近的论文，说明核心技术路线，分析商业机会，下周五给我一份可以用于汇报的成果。”

意图似乎很清楚，但项目还不能直接开始：

- 哪些产品才算“主要产品”？
- “最近的论文”是最近一年、三年，还是五年？
- 最终交付的是报告、演示文稿，还是两者都要？
- 技术分析需要深入到架构、源码，还是概念层面？
- 每个结论需要什么级别的证据？
- 哪些工作可以由 Agent 自主完成？
- “可以用于汇报”具体需要满足什么标准？

`brief-to-build` 会把原始材料转化为已确认的范围、交付物、依赖关系、验收标准、执行步骤和可复用的 Agent Prompt。

不再依赖心灵感应。

## 它会生成什么

使用这个 Skill 会生成三份相互关联的文档：

| 文件 | 你将得到什么 |
|---|---|
| `01_requirements_baseline.md` | 已确认需求、信息来源、目标、范围、交付物、限制条件、授权边界和验收标准 |
| `02_execution_plan_and_prompts.md` | 按依赖关系排列的任务、输出要求、验证方法，以及每个执行阶段可直接使用的 Agent Prompt |
| `03_acceptance_and_change_log.md` | 需求与交付物的映射、验证证据、验收结果，以及后续变更造成的影响 |

三份文档分别回答三个问题：

1. **我们究竟需要交付什么？**
2. **人和 Agent 应该按照什么步骤执行？**
3. **如何证明成果已经完成并且可以验收？**

## 工作流程

```text
领导录音、转写文本、会议纪要、聊天记录或附件
                         ↓
       提取需求、假设、风险和信息缺口
                         ↓
        只澄清真正会影响交付结果的问题
                         ↓
                 生成需求基线
                         ↓
          生成执行步骤与任务级 Agent Prompt
                         ↓
             生成验收与需求变更记录
                         ↓
                 等待明确的执行授权
```

Skill 会严格区分已确认需求、推断、假设、建议、风险和未决问题。假设不会悄悄变成正式需求，建议也不会伪装成已经作出的决定。

## Prompt 示例

```text
请使用 $brief-to-build 分析提供的领导录音、会议转写和参考材料。

生成：
1. 包含可追溯来源的需求基线；
2. 按依赖关系排列的执行计划；
3. 每个执行阶段可直接使用的 Agent Prompt；
4. 验收标准和需求变更记录。

在我明确授权正式执行之前，不要开展调研、编码、部署、
数据修改或外部系统变更。
```

## 适用于真实项目材料

- 领导录音和录音转写
- 客户沟通录音与访谈记录
- 会议纪要
- 聊天和邮件记录
- 项目 Brief 与口头要求
- 参考文档和示例
- 需要重新审阅的已有需求
- 对已确认需求基线提出的新变更

它可以用于技术调研、软件开发、研究报告、演示文稿、数据分析、产品设计、内部工具和多 Agent 协作项目。

## 默认简洁，必要时严格

普通项目使用聚焦的三文档流程。涉及敏感或生产数据、付费服务、不可逆操作、多团队协作、来源冲突、正式审计或完整追溯时，Skill 会启用更严格的检查。

目标是提供足够的结构，避免昂贵的误解——而不是制造多到可以当办公家具的项目文档。

## 安全与执行边界

生成项目计划并不代表已经获得实施授权。正式执行前，Skill 会确认目标、范围、交付物、受众、验收标准、依赖关系，以及外部或不可逆操作的授权。

如果后续要求改变了目标、范围、技术路线、成本、数据、外部系统或验收标准，受影响的工作必须暂停，直到变更被记录并重新确认。
