# Brief to Build

## 目标

把零散或模糊的业务表达转换成有来源、有边界、有任务、有验收标准的项目启动基线。默认使用标准模式；仅在高风险或正式治理场景中升级严格检查。

## 核心规则

1. 先完整读取材料，再提出问题。
2. 区分明确要求、推断、假设、建议和风险；不得把后四类写成已确认需求。
3. 忠实保留“必须、应该、希望、可以、可选、条件成立再做”等原始强度和前提。
4. 只询问会改变目标、核心范围、主要交付物、风险、授权或验收的问题；每轮优先不超过 3—5 个。
5. 对低影响、可撤销且不改变外部状态的事项采用公开默认值。
6. 保留原始材料；默认新建成果，不覆盖或删除既有文件。
7. 未获得明确正式启动授权，只完成需求分析、执行设计和文档审阅。
8. 让每项正式需求都能追溯到来源或用户确认，并映射到任务和验收条件。

## 默认输出

标准模式只维护三份文件：

1. `01_需求基线.md`：合并材料摘要、需求、澄清记录、范围、交付物、授权和验收定义。
2. `02_执行计划与Prompt.md`：合并任务清单、阶段依赖、验证方法和可复制 Prompt。
3. `03_验收与变更记录.md`：合并验收矩阵、验证证据和基线后变更。

使用 [standard-templates.md](references/standard-templates.md) 创建或更新这些文件。用户只需要对话分析时，不创建文件，但仍执行必要门槛检查。

## 简化编号

仅在需要建立映射时使用：

- `REQ-xxx`：已确认或可忠实定位来源的正式需求。
- `Q-xxx`：尚未解决的阻塞问题。
- `TASK-xxx`：产生可验证结果的执行任务。
- `CHG-xxx`：相对已确认基线发生的变更。

使用标签记录“推断、假设、建议、风险”，不为它们强制编号。直接记录来源文件、链接、章节、原话摘要或确认时间；材料多、来源冲突或需要审计时再增加来源编号。

## 标准工作流

### 步骤 1：确认请求和授权

1. 判断用户要的是分析、规划、审阅、变更，还是已经明确授权实施。
2. 确认工作目录、输入材料、输出位置和允许的文件操作。
3. 读取工作区规则、已有需求文件和相关约束。
4. 区分可自行执行、需另行批准和禁止的操作。

**G0 请求边界清楚：** 请求性质、材料范围、工作位置和本轮授权足够明确。未通过时只做安全的只读检查。

### 步骤 2：读取材料并提取需求

1. 完整读取相关材料，标记无法访问、版本冲突和缺失附件。
2. 提取明确要求、推断、假设、建议、风险和潜在问题。
3. 对正式需求执行忠实复述：不增加来源中不存在的方法、指标、受众、优先级或理由。
4. 在需求记录中直接写明来源位置和原始强度。

材料较多时，在 `01_需求基线.md` 中使用材料表；不要默认创建独立材料台账。

### 步骤 3：检查完整性并集中澄清

按八个维度检查：

1. 背景、问题和预期价值。
2. 使用者、决策者和验收人。
3. 目标、非目标和优先级。
4. 范围内、范围外和边界场景。
5. 交付物、受众、深度和格式。
6. 数据、资源、环境、时间和依赖。
7. 质量、证据和验收方式。
8. 授权、安全、合规和重大风险。

先从用户本轮文字、原始材料、确认记录、工作区规则和参考材料中查找答案。材料尚未提供或无法访问时，先请求关键材料和必要路径，不提前罗列可由材料回答的下游问题。只有答案不同会显著改变结果时才创建 `Q-xxx`。每轮集中提出同一主题、不超过 3—5 个阻塞问题并说明影响；其余问题延后，低影响事项采用公开默认值。

**G1 核心条件明确：** 目标、核心范围、主要交付物、受众、验收和授权清楚，不存在开放的阻塞问题。未通过时继续澄清，不设计正式实施任务。

### 步骤 4：形成需求基线

创建或更新 `01_需求基线.md`，至少包含：

- 文档版本、状态和确认信息。
- 背景、目标、非目标和使用方式。
- 已读取材料及缺口。
- 正式需求及来源。
- 推断、假设、建议和风险。
- 范围内、范围外和边界场景。
- 交付物及其深度、格式和受众。
- 数据、资源、依赖、时间和授权边界。
- 每项正式需求的验收条件。
- 已确认事项和非阻塞未决项。

**G2 基线可用：** 基线内部一致、来源清楚、范围明确、主要成果可验收，并标明当前版本和确认状态。

### 步骤 5：形成执行计划和 Prompt

在 G2 通过后创建 `02_执行计划与Prompt.md`。按成果依赖顺序拆任务；每项任务只定义一次，并同时提供对应的可复制 Prompt。写明：

- 对应需求、目标、输入和前置条件。
- 工作内容和明确不做的事项。
- 输出、完成标准、验证方法和证据。
- 可自行执行、需批准和禁止的操作。
- 遇到输入缺失、需求冲突或重大变更时的停止条件。

**G3 执行包闭环：** 每项主要需求都有任务、输出和验证方式；没有孤立任务、无主交付物或超出基线的 Prompt。

### 步骤 6：建立验收与变更记录并等待启动

创建 `03_验收与变更记录.md`，将每个 `REQ` 映射到交付物、通过条件、验证方法、证据位置和结果。基线后发生增删改时，创建 `CHG-xxx`，分析其对范围、任务、Prompt、资源、风险和验收的影响，再更新受影响文件。

完成准备后汇报已确认内容、文件、门槛、风险和建议首个阶段，并停在“等待正式启动”。只有用户明确说“正式开始”或“开始执行第 X 阶段”时才进入实施。

## 正式执行后的约束

本 Skill 负责守住需求和授权基线，具体调研、设计、编码、文档或部署工作交给相应专业 Skill。每阶段执行前重读基线和本阶段 Prompt；执行后保存验证证据并更新验收记录。

遇到会改变目标、核心范围、主要交付物、技术路线、成本、数据、外部系统状态或验收标准的情况，暂停受影响工作，登记变更并取得重新确认。小型、可逆且不扩展范围的实现细节可在既有授权内处理，但要在阶段结果中披露。

## 严格模式升级

出现以下任一情况时，读取并应用 [strict-checks.md](references/strict-checks.md)：

- 多个权威来源互相冲突。
- 涉及敏感数据、生产环境、付费调用或不可逆操作。
- 多团队、多系统或多个主要交付物相互依赖。
- 需要正式审计、合规、签字或完整材料追溯。
- 需求频繁变化，或变化会显著影响成本、时间、架构和验收。
- 用户明确要求完整台账、严格编号或全生命周期治理。

严格模式补充标准流程，不另建一套默认工作流。

## 沟通与停止规则

- 工具操作前说明正在使用本 Skill、当前步骤和授权状态。
- 处理中只报告关键发现、公开假设、阻塞问题和门槛变化。
- 最终先给结论，再列文件、验证结果、未决项、授权状态和下一步。
- 使用可点击的绝对路径链接指向本地成果。
- 不声称读取、确认、验证或测试未实际访问的内容。
- 授权不明、关键输入缺失、权威来源冲突或验收无法定义时，停止受影响工作并请求确认。
