# Brief to Build

## 目标

把零散或模糊的业务表达转成三份有来源、有边界、有步骤、有验证方法的项目文档。兼顾两类读者：让操作者先看懂简明路径，也让执行者能够直接复制任务 Prompt。

本 Skill 只使用标准模式。不要询问用户项目规模，不要让用户选择模式，也不要默认创建额外台账。遇到高风险事项时，仍维护同一套三文档，但要补充授权、风险、证据和停止条件；无法安全继续时请求确认。

## 固定输出

默认只维护三份文件：

1. `01_需求基线.md`：材料摘要、目标、需求、范围、交付物、假设、风险、授权和验收定义。
2. `02_执行计划与Prompt.md`：简明执行路径、任务卡、逐任务 Prompt、总控 Prompt 和需求映射。
3. `03_验收与变更记录.md`：验收矩阵、验证证据、变更记录和遗留问题。

创建或更新这些文件前，完整读取 [references/standard-templates.md](references/standard-templates.md)。用户明确只要对话分析时，可以不创建文件，但仍执行必要门槛检查。

## 核心规则

1. 先完整读取材料，再提出问题。
2. 区分明确要求、推断、假设、建议和风险；不得把后四类写成已确认需求。
3. 忠实保留“必须、应该、希望、可以、可选、条件成立再做”等原始强度和条件。
4. 只询问答案不同会改变目标、核心范围、主要交付物、成本、风险、授权或验收的问题。每轮集中在一个主题，优先不超过 3—5 个问题。
5. 对低影响、可撤销、无费用且不改变外部状态的事项采用公开默认值。
6. 保留原始材料；默认新建成果，不覆盖或删除无关既有文件。
7. 未获得明确正式启动授权，只完成需求分析、执行设计、Prompt 编写和文档审阅。
8. 每项正式需求都要能追溯到材料或用户确认，并映射到任务和验收条件。
9. 执行计划先讲清主路径，再展开细节；优先使用日常语言，首次出现的专业术语要解释。
10. 每项任务只定义一次；阶段 Prompt 引用需求基线，不重复堆砌整份需求。

## 简化编号

仅在建立映射时使用：

- `REQ-xxx`：有明确材料来源或用户确认的正式需求。
- `Q-xxx`：答案不同会显著影响结果的开放问题。
- `TASK-xxx`：产生可验证结果的执行任务。
- `CHG-xxx`：相对已确认基线发生的变更。

用“推断、假设、建议、风险”标签记录其他信息，不强制增加更多编号体系。

## 标准工作流

### 步骤 1：确认请求与授权

1. 判断用户要的是分析、规划、审阅、变更，还是已明确授权实施。
2. 确认输入材料、工作目录、输出位置和允许的文件操作。
3. 读取工作区规则、已有需求文件和相关约束。
4. 区分可自行执行、需另行批准和禁止的操作。

**G0 请求边界：** 请求性质、材料范围、工作位置和本轮授权明确。未通过时只做安全的只读检查。

### 步骤 2：读取材料并提取需求

1. 完整读取所有相关材料，标记无法访问、版本冲突和缺失附件。
2. 提取明确要求、推断、假设、建议、风险和潜在问题。
3. 对正式需求忠实复述，不增加来源中不存在的方法、指标、受众、优先级或理由。
4. 直接记录文件、章节、时间点、链接或用户确认时间，不为少量材料另建来源台账。

### 步骤 3：检查完整性并集中澄清

检查以下八个维度：

1. 背景、问题和预期价值。
2. 使用者、决策者和验收人。
3. 目标、非目标和优先级。
4. 范围内、范围外和边界场景。
5. 交付物、受众、深度和格式。
6. 数据、资源、环境、时间和依赖。
7. 质量、证据和验收方式。
8. 授权、安全、合规和重大风险。

先从现有材料寻找答案。仅当缺失答案会显著改变结果时创建 `Q-xxx`；其他事项记录为非阻塞未决项或公开默认值。

**G1 核心条件：** 目标、核心范围、主要交付物、受众、验收和授权足够清楚，不存在开放的阻塞问题。未通过时继续澄清，不设计正式实施任务。

### 步骤 4：形成需求基线

创建或更新 `01_需求基线.md`。至少写明文档状态、项目摘要、材料与缺口、正式需求及来源、推断/假设/建议/风险、范围、交付物、资源依赖、授权边界、验收定义和确认记录。

**G2 基线可用：** 内容内部一致、来源清楚、范围明确、主要成果可验收，并标明版本和确认状态。

### 步骤 5：形成面向操作者的执行计划和 Prompt

在 G2 通过后创建或更新 `02_执行计划与Prompt.md`，使用双层结构：

1. **简明执行路径：** 用 5—8 步说明“做什么、得到什么、何时完成、对应任务”。让操作者先看这一节就能理解项目主线。
2. **详细任务卡：** 每项任务写明目标、开始前、具体步骤、输出、完成标准、验证方法、授权边界、停止条件和状态。

每项任务附一段可独立复制的 Prompt，使用直白结构：

```text
请使用 $brief-to-build 执行 TASK-xxx「任务名称」。

【依据与输入】需求基线、准确路径、上一任务结果。
【目标】本阶段要形成的可验证结果。
【具体步骤】按顺序列出动作和验证动作。
【输出】准确文件或目录。
【完成标准】逐条可检查条件。
【不要做】范围外或未授权事项。
【授权边界】可执行、需批准和禁止事项。
【停止条件】输入缺失、冲突、重大变更或风险。

完成后汇报输出、验证结果、失败与遗留问题，并更新验收记录。
```

在所有任务后提供一个总控 Prompt。总控 Prompt 必须要求：按依赖顺序推进、一次只执行一个已授权任务、先检查前置条件、完成后保存证据并更新三文档、遇到重大变更先停止。

**G3 执行包闭环：** 每项主要需求都有任务、输出、验证方式和验收项；每个阶段都有 Prompt；没有孤立任务、无主交付物或超出基线与授权的内容。

### 步骤 6：建立验收与变更记录并等待启动

创建或更新 `03_验收与变更记录.md`，把每个 `REQ` 映射到交付物、通过条件、验证方法、证据位置和结果。

基线确认后发生增删改时创建 `CHG-xxx`，分析它对目标、范围、交付物、任务、Prompt、资源、风险和验收的影响，再更新全部受影响文档。基线确认前的澄清直接更新草案版本，不伪装成已批准变更。

完成准备后汇报文件、门槛、风险、仍需确认事项和建议首个任务，并停在“等待正式启动”。只有用户明确说“正式开始”或“开始执行 TASK-xxx/第 X 阶段”时才进入实施。

## 正式启动后的约束

本 Skill 负责守住需求、授权和验收基线。具体调研、设计、编码、文档或部署工作交给相应专业 Skill。

每项任务执行前重读需求基线和任务卡；执行后保存命令、日志、测试、截图、结果文件或审阅记录等证据，并更新验收记录。遇到会改变目标、核心范围、主要交付物、技术路线、成本、数据、外部状态或验收标准的情况，暂停受影响工作并登记变更。

## 表达要求

- 结论先行，句子简短，优先使用操作者熟悉的词。
- 简明路径不塞入完整治理字段；详细控制放在任务卡。
- “完成标准”写成可检查状态，不使用“较完整”“效果良好”等模糊措辞。
- 不把未读取、未验证或未运行的内容写成已确认事实或实测结果。
- 阶段汇报只包含：结论、输出、验证、失败/遗留、授权状态和下一步。
